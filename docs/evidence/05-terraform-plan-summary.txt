Explicitly ABSENT from this plan (by design, not by omission):
- aws_eks_node_group  — replaced with self-managed launch template + ASG,
  because this KodeKloud sandbox account's IAM policy does not grant
  eks:CreateNodegroup (confirmed via aws iam simulate-principal-policy, a
  read-only permission check — no resources were created just to test this).
- aws_db_instance / RDS — this account's IAM policy does not grant
  rds:CreateDBInstance either. Gated behind a clean `enable_rds` variable
  (default true; false only in this session's gitignored tfvars) rather
  than deleted from the codebase or worked around with `-target`.

--- Why the architecture differs from a standard EKS setup ---
Confirmed via `aws iam simulate-principal-policy` (read-only; the specific
commands and full reasoning are in docs/phases.md's Phase 6 notes):
- eks:CreateCluster: allowed
- iam:PassRole to eks.amazonaws.com: allowed ONLY for a role named exactly
  "eksClusterRole" (not any name) — this project's EKS module has a
  `cluster_iam_role_name` override variable specifically for this.
- eks:CreateNodegroup: not granted by any attached policy.
- eks:CreateFargateProfile: explicitly denied.
- ec2:RunInstances, autoscaling:CreateAutoScalingGroup, iam:PassRole to
  ec2.amazonaws.com: all allowed — the self-managed worker node path.
- rds:CreateDBInstance: not granted by any attached policy.
